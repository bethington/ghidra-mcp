# Era toolchains (gitignored — provenance + how to re-create)

This directory is named `vc6` for historical reasons. It now holds **two**
toolchains, and **VS2003 is the one that matters for D2**.

| Dir | What | Role |
| --- | --- | --- |
| `VS7/` | Visual Studio .NET 2003 **RTM** — `cl.exe` 13.10.3077, `link.exe` 7.10.3077 | **Primary.** The compiler family that built D2 1.13c. |
| `VC98/` | Visual C++ 6.0 SP6 — `cl.exe`, headers, libs | Fallback; also the only source of Win32 Platform SDK headers (`windows.h`, `winbase.h`) here. |
| `COMMON/` | shared VC6 bits | — |

### RTM vs SP1 — the gap is real, and it is now closed

D2's Rich headers say build **6030** = VS2003 **SP1**. What is vendored here
is **RTM (3077)**; SP1 was a separate download and is not on the Pro media.

Measured 2026-08-08, RTM is byte-exact everywhere it had been checked:

* all 103 FID-identified CRT functions in `Game.exe` match RTM's own
  `VS7/Lib/libcmt.lib` **exactly**;
* hand-written C compiled by RTM's `cl` reproduced
  `DATATBLS_FindConfigOptionIndex` to the byte.

That earlier reading — "whatever SP1 changed, it was not these CRT objects" —
generalised from those 103 and was **wrong as a general claim**. A real SP1
toolchain now exists at **`C:\VS2003`** (`cl` 13.10.6030, `link` 7.10.6030,
install-free and relocatable; see `C:\VS2003\_provenance\README.md` for how it
was built and how to rebuild it). Comparing the two `libcmt.lib` directly —
code sections only, relocations masked, via
`C:\VS2003\_provenance\compare_libcmt_text.py`:

* **562 of 644 code-bearing objects (87.3%) are byte-identical** between RTM
  and SP1. That is why the 103 matched: they live in this majority.
* **82 objects (12.7%) genuinely differ**, among them `output.obj` /
  `input.obj` (the entire printf/scanf family), `cprintf`, `cscanf`,
  `calloc`, `getcwd`, `assert`, `setlocal` and the `stat` family.

Whole-object comparison instead reports 93.9% changed; almost all of that is
embedded version metadata rather than instructions, so it overstates the gap
badly. The 12.7% figure is the one to reason from.

The **complete list of all 82**, with per-object code sizes and deltas, is at
`C:\VS2003\_provenance\libcmt_rtm_vs_sp1.md` (`.json` alongside it for machine
use), regenerated by `compare_libcmt_report.py`. Worth knowing before you rely
on the summary: every one of the 82 also differs whole-member, **none changed
code without also changing size**, and they cluster by family rather than
scattering — printf/scanf, `stat`, file/directory ops, locale/MBCS, float
conversion, heap, and SEH/diagnostics (`secfail.obj` among them). Deltas are
small and mostly positive, clustered at +4/+5/+10, which reads as broad
security hardening; the `stat` family is the outlier at roughly -140 bytes
each, a genuine rewrite.

Practical rule: those 82 objects are exactly where an RTM-based byte-match
produces a **false negative** against SP1-built D2 code. Prefer `C:\VS2003`
for `CONF_BYTEMATCH` work. RTM remains fine for the 87% — including everything
certified so far — so nothing already proven needs revisiting.

Note the vendored `VS7/` tree here is still RTM and is deliberately left
alone: the benchmark's `runs/latest.json` baselines were produced with it, and
swapping the compiler under them would move scores for a reason unrelated to
documentation quality. Retarget it only as a deliberate, separately measured
change. A freshly built `Benchmark.dll` therefore still carries build **3077**
where D2's carries **6030**.

## Why VS2003 is the right compiler (measured, not assumed)

Rich-header product IDs of the shipped binaries name their own compiler:

* `Game.exe` (PD2-S12): 89 × `Utc1310_C` build **6030**, 20 × masm 6030,
  2 × `Utc1310_CPP` 6030 — and **zero** VC6 (VC6 SP6 is build 8804).
* D2Common / D2Client / D2Game / Fog / Storm: same, all 710-series 6030.

Build 6030 = **VS .NET 2003 SP1**.

Corroborated by exact bytes: every one of the 103 FID-identified CRT
functions in `Game.exe` is byte-identical (relocations masked) to its object
in `VS7/Lib/libcmt.lib`. The same comparison against `VC98/LIB/LIBCMT.LIB`
matches only 11/103 (10.7%), and those 11 are tiny SEH/mbcs helpers that
happen to be identical in both toolchains.

## The `msvcp71.dll` gotcha (fixed 2026-08-08)

`VS7/Bin/cl.exe` spawns `c1.dll`, which imports six `std::basic_string`
symbols from **`MSVCP71.dll`**. That DLL was missing from this tree and from
the whole machine, so `cl.exe` failed with:

```
cl : Command line error D2027 : cannot execute '...\VS7\Bin\c1.dll'
```

`link.exe` was unaffected (it needs only `mspdb71` + `msvcr71`, both
present) — **which is exactly why `build.py`'s `vc6sp6` toolchain pairs
VC6's compiler with VS2003's linker.** That combination reproduces the PE /
Rich-header shape but *not* compiler codegen, so it cannot byte-match
authored D2 code.

Fixed by copying `msvcp71.dll` (+ `.pdb`) here from the VS2003 Pro
installation media. With it in place `cl.exe` runs and byte-matching works
(see below).

## Verified byte-match recipe

`DATATBLS_FindConfigOptionIndex` @ `0x004078e0` in PD2-S12 `Game.exe`,
92 bytes / 1 relocation / 88 informative bytes — **exact match**:

```c
#define ARRAY_SIZE(a) (sizeof(a)/sizeof((a)[0]))
int __stdcall F(const char *s) {
    unsigned i;
    for (i = 0; i < ARRAY_SIZE(gaCmdArguments); i++)
        if (0 == strcmp(gaCmdArguments[i].szCommand, s)) return i;
    return -1;
}
```

`VS7/Bin/cl.exe /c /O2` (also matches under `/Ox`, `/O2 /Ob0`, `/O2 /Gy`,
`/O2 /GF`, `/O2 /Oa` — codegen is robust across those, so no fragile flag
archaeology is needed).

Two findings worth keeping:

* **The loop comparison must be UNSIGNED.** `for (int i = 0; i < 57; i++)`
  emits `JL` and is 96 bytes; the original emits `JB`. Any `ARRAY_SIZE`
  (sizeof-based, hence `size_t`) or an `unsigned` counter produces the
  match — and `int i < ARRAY_SIZE(...)` works too, because `i` promotes.
* **VC6 matched none of the variants**, at any flag setting. The compiler
  identity is not a detail.
